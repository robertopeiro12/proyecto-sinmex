# Operación → Procesos (PR A) — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** pantalla *Operación → Procesos* con la tarjeta de cliente y las pestañas Merma, Cambios, Consumos, Promoción y
Descuentos (captura arriba + lista del día abajo), y que lo capturado a nombre de un vendedor cuente en su corte.

**Architecture:** tablas nuevas `proceso_oficina` + `proceso_oficina_linea`; backend en `apps/backend/src/modules/inventario/`
(`procesos.*` + reglas puras `reglas-procesos.ts`), endpoints `/procesos`; `movimientosDelDia`
(`produccion/cortes.repository.ts`) suma también `proceso_oficina`, así corte, Inventario por vendedor y el candado de la
venta del portal lo ven solos. Portal en `apps/portal/src/components/procesos/` + `lib/procesos.ts`.

**Tech Stack:** Postgres/Supabase (migración + pgTAP), NestJS + Kysely + Jest, Next.js + Vitest.

**Spec:** `docs/superpowers/specs/2026-11-25-procesos-design.md` (boceto aprobado: `docs/superpowers/specs/img/2026-11-25-procesos-boceto-merma.png`)

## Global Constraints

- Migración `supabase/migrations/20261126120000_procesos.sql` (versión única: revisar `ls supabase/migrations` y ramas abiertas).
- `tipo` ∈ `merma|cambio|consumo|promocion|descuento`; `merma_de` ∈ `cliente|almacen` solo en merma (nulo en los demás); `sentido` ∈ `recibido|entregado`; piezas 1..100000; máx. 200 líneas; una línea por (presentación, sentido); comentario 1..300 recortado o `null`.
- Por tipo: merma de cliente y cambio = cliente obligatorio, líneas recibido y entregado, **total entregado = total recibido**; merma de almacén = sin cliente, solo recibido; consumo = sin cliente, solo entregado; promoción = cliente obligatorio, solo entregado; descuento = **vendedor obligatorio**, sin cliente, solo entregado.
- `vendedor_id` null = **Oficina** (no permitido en descuento). Vendedor y cliente vivos y de la sucursal del proceso.
- Fecha: hoy o anteriores en Tijuana (`reglas-comunes.ts`). Alcance de sucursal como Registro de Operación: atado a otra = 403 al listar, proceso de otra sucursal = 404, `todas` = 400 "Elige una sucursal.".
- Permisos (grupo `Operacion Comercial`, exigidos en el servicio por tipo con `PermisosRepository.permisosDe`, como `operaciones-almacen`): `proceso.merma`, `proceso.cambio`, `proceso.consumo`, `proceso.promocion`, `proceso.descuento`. Sin el del tipo = 403.
- Corte (con vendedor): merma de cliente → `mermaRecibida`/`mermaEntregada`; merma de almacén → `mermaAlmacen`; cambio recibido/entregado → `cambiosRecibidos`/`cambiosEntregados`; consumo → `consumo`; promoción → `regaladas`; descuento → nada. Solo filas vivas.
- Textos en español; piezas de `components/ui/`; `useConfirmar` (nunca `window.confirm`); cabe a 1366 px sin desplazamiento lateral. Tipos duplicados backend ↔ portal en el mismo commit.
- Roberto tiene backend (3010) y portal (3001) prendidos: no apagar, **no correr `npm run build`**. Migración solo a la base LOCAL (`npm run supabase -- migration up --local`; nunca `db reset` ni la nube).

## Review Focus

1. Editar un proceso cambiando el vendedor: el corte del anterior pierde las piezas y el del nuevo las gana; eliminarlo las quita. → e2e Tarea 3.
2. Un cliente o vendedor de otra sucursal (o dado de baja) se rechaza con 400, no se guarda a otra sucursal. → e2e Tarea 2.
3. Merma de cliente que no cuadra (5 recibidas, 3 entregadas) = 400 en el servidor aunque el portal lo impida. → e2e Tarea 2.
4. Precarga de descuentos de un vendedor sin corte hecho: `corteHecho: false` y sin líneas; con corte, solo los faltantes positivos de piezas por presentación. → e2e Tarea 3.
5. Cambiar de cliente o de pestaña no deja lo escrito de otro cliente en la captura; la lista muestra solo lo del cliente elegido. → prueba Tarea 4.

### Tarea 1: Migración y pgTAP
**Files:** `supabase/migrations/20261126120000_procesos.sql`, `supabase/tests/99_procesos_test.sql`, `apps/backend/src/database/schema.d.ts` (`npm run db:types --workspace=apps/backend`).
- `proceso_oficina`: `id uuid pk default gen_random_uuid()`, `tipo`, `sucursal_id` → sucursal, `fecha date`, `cliente_id` → cliente null, `vendedor_id` → vendedor null, `merma_de` null, `comentario` null, `capturo_usuario_id` → usuario not null, `actualizado_por_usuario_id` null, `created_at`/`updated_at` (trigger genérico de `updated_at`), `deleted_at`. Checks **totales** (`case … else`, no lógica trivalente): tipo; merma_de según tipo; cliente obligatorio en cambio, promoción y merma de cliente, nulo en consumo, descuento y merma de almacén; vendedor obligatorio en descuento; comentario 1..300.
- `proceso_oficina_linea`: `id`, `proceso_id` → proceso_oficina, `presentacion_id` → presentacion, `sentido`, `piezas` 1..100000, `unique (proceso_id, presentacion_id, sentido)`. Índices: `proceso_oficina (sucursal_id, tipo, fecha) where deleted_at is null` y `(vendedor_id, fecha) where deleted_at is null`.
- Los 5 permisos con descripción en español ("Procesos: merma de clientes y almacén", …).
- [ ] pgTAP que falla (cada check rechaza su combinación inválida y acepta la válida de cada tipo; permisos presentes) → migración → `npm run supabase -- migration up --local` y `npm run supabase -- test db` PASS → probar en autocommit como el CI (base temporal `prueba_ci`, todas las migraciones con `psql -v ON_ERROR_STOP=1 -f`; borrarla) → db:types → **Commit** `Procesos: migración (proceso_oficina y permisos)`.

### Tarea 2: Backend — reglas y CRUD
**Files:** `apps/backend/src/modules/inventario/{reglas-procesos.ts,reglas-procesos.spec.ts,procesos.repository.ts,procesos.service.ts,procesos.controller.ts,dto/proceso.dto.ts}`, `inventario.module.ts`, e2e `apps/backend/test/procesos.e2e-spec.ts`.
**Produces:**
```ts
type TipoProceso = 'merma' | 'cambio' | 'consumo' | 'promocion' | 'descuento';
interface LineaProceso { presentacionId: string; nombre: string /* "Horchata 500 ml" */; sentido: 'recibido' | 'entregado'; piezas: number }
interface Proceso { id: string; tipo: TipoProceso; fecha: string; hora: string /* 'HH:MM' Tijuana */;
  mermaDe: 'cliente' | 'almacen' | null; cliente: { id: string; nombre: string } | null;
  vendedor: { id: string; nombre: string } | null /* null = Oficina */; comentario: string | null;
  capturo: string; lineas: LineaProceso[]; actualizadoEn: string }
// reglas-procesos.ts
function validarProceso(e: EntradaProceso): { ok: true; valor: EntradaProcesoLimpia } | { ok: false; error: string };
```
Endpoints: `GET /procesos?tipo&fecha&sucursal&cliente?` → `{ fecha, hoy, procesos: Proceso[] }` (orden por hora; `cliente` filtra); `POST /procesos` `{ tipo, sucursal, fecha, clienteId, vendedorId, mermaDe, comentario, lineas: {presentacionId, sentido, piezas}[] }` → `Proceso`; `PATCH /procesos/:id` (lo mismo sin `tipo` ni `sucursal`) → `Proceso`; `DELETE /procesos/:id` → 204 (baja lógica). Editar bloquea la fila `for update`.
- Mensajes del error de cuadre: `"Lo entregado (3) no cuadra con lo recibido (5)."`.
- Presentación: nueva = activa y viva; al editar se conserva una línea existente aunque ya no lo esté si no cambia.
- [ ] Unit de `validarProceso` (cada tipo válido; cada regla del Global Constraints rota da su error; cuadre 5/5 ok y 5/3 error; recorte del comentario) → e2e (alta/lista/edición/baja por tipo; 403 sin el permiso del tipo; Review Focus 2 y 3; fecha futura 400; `todas` 400; otra sucursal 404; descuento sin vendedor 400) → implementar → pasan; `npm test --workspace=apps/backend`, e2e `procesos`, lint → **Commit** `Procesos: backend (captura, lista, edición y baja)`.

### Tarea 3: Backend — corte, precarga de descuentos y resumen del cliente
**Files:** `produccion/cortes.repository.ts` (`movimientosDelDia`), `produccion/reglas-corte.ts` (quitar "valen 0 hasta T-33" de los comentarios), `inventario/procesos.*`, e2e `procesos-corte.e2e-spec.ts`.
**Produces:**
- `movimientosDelDia` agrega un `union all` desde `proceso_oficina` vivo con `vendedor_id` no nulo y líneas, con el mapeo del Global Constraints; `cambiosEntregados`/`cambiosRecibidos` dejan de ser `0` fijos.
- `GET /procesos/descuentos/precarga?vendedor&fecha` (permiso `proceso.descuento`) → `{ corteHecho: boolean; lineas: { presentacionId: string; nombre: string; piezas: number }[] }`: con corte hecho, las presentaciones con `faltante > 0` del corte de ese vendedor y fecha (de `reglas-corte.ts`, sin recalcular); sin corte, `[]`. Vendedor ajeno o dado de baja = 404.
- `GET /procesos/cliente/:id` (cualquiera de los 5 permisos) → `{ id, nombre, tipo: 'cliente'|'prospecto', tipoNegocio: string|null, diasCredito: number|null, deudaCentavos: number, notasConSaldo: number, ultimaCompra: string|null /* AAAA-MM-DD */, promociones: string[] }`. Deuda y notas = ventas vivas a crédito `pendiente`/`abonado` con saldo > 0 fuera de cuenta perdida (la regla de "nota con saldo" de `rutas/notas-ruta.repository.ts`: reutilízala, no la dupliques); promociones vivas que aplican al cliente con `textoPromocion` (`cartera-clientes/promociones-texto.ts`). Cliente de otra sucursal = 404.
- [ ] e2e que falla (Review Focus 1 y 4; merma de cliente, merma de almacén, cambio, consumo y promoción con vendedor cambian la teórica de su corte en el campo correcto; con Oficina no cambian; descuento no cambia nada; resumen con deuda y promociones) → implementar → pasan, más `corte`, `inventario-vendedor` y `ventas-inventario` e2e sin regresiones, `npm test`, lint → **Commit** `Procesos: cuentan en el corte, precarga de descuentos y resumen del cliente`.
